1. SUMMARY

Graft is a code-graph tool for AI coding agents. The command "graft init"
writes an MCP server entry into the configuration files of the agent hosts,
for example ".mcp.json" for Claude Code.

Graft is meant to write the entry "graft mcp" when the "graft" program is
installed. Graft is meant to write "npx -y @nanonets/graft mcp" only when
"graft" is not installed.

On Windows the check for an installed "graft" always fails. Graft therefore
writes the "npx" form every time, also on machines where "graft" is installed.

The "npx" form has no version. Each time the agent starts the MCP server,
npm downloads and runs the package version that the npm registry serves at
that moment. The "-y" flag removes the confirmation prompt.

A compromised registry release of @nanonets/graft, or of one of its
dependencies, would run on every machine that uses this entry. It would run
at the start of each agent session.


2. AFFECTED SYSTEMS

- All platforms: the fallback entry has no version pin.
- Windows: the entry is the default, because the check always fails.
- POSIX systems: the entry is written only when "graft" is not on PATH.
- Trail brand (@trailhq/trail-code, release 0.23.0): upstream writes
  "npx -y @trailhq/trail-code mcp" in the same way when the probe fails.

Files that Graft writes with this entry include:

  .mcp.json                        (Claude Code, project scope, often committed)
  ~/.claude.json                   (Claude Code, user scope)
  .cursor/mcp.json
  .gemini/settings.json
  ~/.gemini/config/mcp_config.json
  .kiro/settings/mcp.json
  .grok/config.toml
  ~/.codex/config.toml
  opencode.json

The session-start hook of Graft also rewrites these entries when the Graft
version changes. A manual correction is therefore not permanent on Windows
(see section 7).


3. TECHNICAL DETAILS

3.1 The check

File: src/hosts/mcp-config.ts, function graftOnPath().

    function graftOnPath(): boolean {
      const r = spawnSync('graft', ['--version'], { stdio: 'ignore', timeout: 5000 });
      return r.status === 0;
    }

The call does not use a shell. On Windows, npm installs "graft" as a
"graft.cmd" shim. A call to spawnSync without a shell cannot start a shim.
Observed results on Windows 11, Node.js 26.7.0, with Graft installed and on
PATH:

    spawnSync('graft', ['--version'])      -> status null, error ENOENT
    spawnSync('graft.cmd', ['--version'])  -> error EINVAL
    spawnSync('graft', ..., {shell: true}) -> ETIMEDOUT at 5 seconds

The EINVAL result is the expected effect of the Node.js change for
CVE-2024-27980. That change blocks the start of .cmd and .bat files
without a shell. The shell variant is not a good repair: "graft --version"
takes about 2.5 seconds on the test machine, and the 5 second limit was
reached.

Because the function returns false, serverEntry() selects the fallback.

3.2 The fallback

File: src/hosts/mcp-config.ts.

    const NPX_LAUNCH = { command: 'npx', args: ['-y', '@nanonets/graft', 'mcp'] };

The package name has no version. npm resolves the "latest" tag at the time
of each start.

3.3 Why the two faults add up

Each fault is small alone.

- Without the Windows fault, only machines without "graft" use the "npx" form.
- Without the missing pin, the "npx" form would run a fixed version.

Together they make an unpinned, unreviewed download the normal start path for
every Windows user. This path runs in every repository that Graft wires.


4. REPRODUCTION

Verified on Windows 11, Node.js 26.7.0, Graft 0.21.1 installed with
"npm install -g". The command "graft" works in a terminal.

Step 1. In a clone of the Graft source, run:

    node_modules/.bin/tsx -e "import {serverEntry} from './src/hosts/mcp-config.ts'; console.log(JSON.stringify(serverEntry()))"

Result:

    {"command":"npx","args":["-y","@nanonets/graft","mcp"]}

The expected result is {"command":"graft","args":["mcp"]}.

Step 2. The same entry was found in the ".mcp.json" files of two real
repositories on the test machine. Graft wrote them. The reporter did not
re-run "graft init" in a clean repository for this report. The code path is:
"graft init" calls serverEntry() in src/claude/init.ts and
src/hosts/claude-global.ts.

Upstream main uses the same function (checked with "git grep" at fe30ead).


5. IMPACT AND SEVERITY

What an attacker needs: control of a release of @nanonets/graft, or of a
dependency of it, on the npm registry. This can happen through theft of a
maintainer account or token, or through a malicious dependency update.
Graft is an npm package with install scripts and native grammar
dependencies, so a bad release can run code at install time.

What the attacker gets: code execution with the rights of the user, on every
machine that starts the MCP server with this entry. The next agent session
starts the new code. No new user action is needed.

Why this is worse than a normal install of the package:

- A global install runs the code that the user chose and installed once.
  The "npx -y" entry fetches again at each start.
- The entry is often in ".mcp.json", which projects commit. One committed
  file can send this trust decision to every contributor.
- The user does not see a new version. There is no lock file and no review.

Limits of this finding:

- There is no exploit for Graft itself. The attack needs a prior
  compromise of the registry supply chain.
- The same risk exists for any tool that documents "npx -y <package>" for
  MCP servers. The Graft README shows this form.
- Claude Code asks the user to approve a project MCP server on first use.
  The reporter did not test whether it asks again when the package version
  behind the same command changes. Do not assume that it does.

Suggested rating, reporter's estimate only: low to medium. A CVSS 3.1 vector
is not given, because the attack complexity depends on events outside
Graft.


6. WORKAROUND FOR USERS

1. Install Graft globally: npm install -g @nanonets/graft
2. In each project, edit the Graft entry in ".mcp.json" and the other files
   in section 2 to read:

       "graft": { "command": "graft", "args": ["mcp"] }

3. Check the entry again after each Graft upgrade (see section 7).

To pin the fallback by hand, use "@nanonets/graft@<version>" in place of
"@nanonets/graft". Use the exact version that you reviewed.


7. RESIDUAL BEHAVIOUR WITHOUT THE PATCH

The Graft session-start refresh rewrites the entry when the stamp version
differs from the running version. On Windows, the rewrite writes the "npx"
form again. A manual correction can therefore revert after an upgrade.


8. PATCH

The patch below applies to upstream main at commit fe30ead.
It makes two changes:

a) It replaces the spawn check with a file system search of PATH. The search
   uses PATHEXT on Windows and the execute bit on POSIX. It does not start a
   process. It has no time limit and no shell.

b) It pins the "npx" fallback to the running Graft version:
   "@nanonets/graft@<version>". If the version cannot be read (0.0.0), the
   fallback stays unpinned.

The runningVersion() function moves from src/upkeep.ts to src/cli-meta.ts.
This avoids an import cycle. src/upkeep.ts exports the function again, so
existing imports still work.

The patch does not remove the "npx" fallback. A stricter policy is possible:
always write "graft mcp" and print a warning when "graft" is not on PATH.
That policy changes behaviour for users who run "npx @nanonets/graft init"
without a global install. The maintainers should decide on it.

Save the text between the two marker lines to a file, without the marker
lines. Then run:

    git apply --check graft-mcp-launcher.patch
    git apply graft-mcp-launcher.patch
